# GitHub issue の作り方

ブレストで固めた要件・設計を、`gh` CLI で GitHub issue に落とし込む手順。
issue はリポジトリ外に公開される成果物なので、**必ずユーザーの明示的な承認を得てから作成する**。

## 前提の確認

- `gh` が使えて認証済みか（不明なら `gh auth status`）。未認証ならユーザーに案内し、勝手に進めない。
- issue にする内容（要件・設計）がユーザーと合意済みか。まだなら SKILL.md のワークフローに戻る。

## 手順

### 1. 作成内容をユーザーに最終確認する

「以下の内容で issue を作成してよいか」を、タイトル案・本文の要点とともに提示して承認を得る。
併せて確認するとよい点: 付けるラベル、担当者やマイルストーンの要否。承認が取れるまで `gh` は実行しない。

### 2. リポジトリの慣習に合わせる

- **言語**: リポジトリの既存 issue・コミットに合わせる（このリポジトリは日本語）。
- **ラベル**: `gh label list` で存在するラベルを確認し、内容に合うものだけを付ける。
  無理に付けない。存在しないラベルを新規作成するのは、ユーザーが望んだときだけ。
- **タイトル**: 簡潔で動作が分かる要約にする（例: 「検索コマンドに JVN ID 指定を追加する」）。
  issue はコミットではないので `feat:` などの Conventional Commits プレフィックスは必須ではない。
  ただし、対応する変更が想定する type（feat/fix/refactor 等）を本文で触れておくと後工程が楽。

### 3. 本文を一時ファイルに書き出す

本文は複数行・日本語を含むため、シェルのエスケープ事故を避けて **一時ファイル**に書き、
`--body-file` で渡す。テンプレートは下記「issue 本文テンプレート」を使う。
一時ファイルはスクラッチパッド領域など作業用の場所に置く。

### 4. `gh issue create` で作成する

コマンドは1行で実行する（複数コマンドを `;` / `&&` で連結しない）。

```
gh issue create --title "<タイトル>" --body-file "<本文ファイルのパス>"
```

ラベルを付ける場合は `--label "<label1>" --label "<label2>"` を足す。
担当者は `--assignee "@me"`、マイルストーンは `--milestone "<名前>"` で指定できる（必要なときだけ）。

### 5. 結果を報告する

作成に成功すると issue の URL が出力される。その URL をユーザーに伝えて完了。
本スキルの責務はここまで（実装前の合意形成と issue 化）。実装は別途着手する。

## issue 本文テンプレート

過不足を調整してよいが、**背景・目的・要件・採用案・成功基準**は原則残す。
検討した代替案を残すと「なぜこの設計にしたか」が後から辿れる。

```markdown
## 背景 / 課題
<!-- なぜこれが必要か。解決したい問題・現状の不便。 -->

## 目的 / ゴール
<!-- この変更で達成したいこと。 -->

## スコープ外 (Non-goals)
<!-- 今回はやらないこと。認識ズレ防止のため明示する。 -->

## 要件
<!-- 機能要件・制約（技術/互換性/パフォーマンス等）を箇条書きで。 -->

## 採用する設計案
<!-- 選んだアプローチの概要。データフローや影響範囲、対応する変更の type にも触れる。 -->

### 検討した代替案
<!-- 見送った案とその理由。将来の再検討の手がかりになる。 -->
- 案B: … / 見送り理由: …

## 実装ステップ
<!-- 段階分け。各段階が独立して意味を持つよう分ける。 -->
1. …
2. …

## 成功基準 / 受け入れ条件
<!-- どうなれば完了か。テスト観点も含める。 -->
- [ ] …

## 補足
<!-- 図・参考リンク・関連 issue/PR など。 -->
```
