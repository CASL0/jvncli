# Brainstorming（実装前の要件・設計固め）

実装に入る前に、ユーザーのアイデアを **意図 → 要件 → 設計** の順で一緒に磨き上げ、
合意できたら **GitHub issue** に落とし込むためのスキル。

## なぜ先にブレストするのか

コードを書き始めてから「そもそも何を作りたかったのか」がズレていると、手戻りが最も高くつく。
先に目的・制約・成功基準・設計の選択肢を言語化しておけば、実装は「決まったことを書くだけ」になり、
レビューや後日の見返しも issue 1 枚で完結する。急いで実装に飛びつかず、まずここで土台を固める。

## いつ使う / いつ使わない

**使う:** 新機能、新しいコンポーネント／モジュール、既存機能への追加、挙動の変更、
設計上の判断が絡むリファクタなど、「何を・どう作るか」に選択の余地がある作業。

**使わない:** タイポ修正、フォーマット適用、原因が自明な1行バグ修正、依存の定期更新など、
設計判断を伴わない機械的な作業。ここでブレストを挟むと過剰になる。判断に迷ったら、
「実装方針に 2 通り以上ありうるか？」を基準にする。ありうるなら使う。

## ワークフロー

以下を順に進める。各ステップの狙いを理解した上で、機械的になぞるのではなく対話として運ぶこと。

### 1. プロジェクトのコンテキストを確認する

提案は必ずこのリポジトリの実態に沿わせる。実装差分ではなく **設計判断に効く情報**を先に集める。

- `CLAUDE.md` と `.claude/rules/`（あれば）— アーキテクチャ・コーディング規約・Git 運用。
- 関連しそうな既存コード・モジュール構成 — 命名やレイヤ分けの流儀。
- 直近のコミット (`git log --oneline -20` 相当) と関連 issue／PR — 進行中の方向性。
- issue の運用慣習 — 言語（このリポジトリは日本語）、`.github/ISSUE_TEMPLATE/`、ラベル（`gh label list`）。

集めた内容から、ユーザーが明示していない前提・制約を拾い、次の質問の材料にする。

### 2. 明確化の質問を「1つずつ」する

要件が曖昧なまま設計に進まない。質問は **一度に1問**。回答を受けてから次を組み立てる。

- 一度に多くを聞くとユーザーが疲れ、回答が浅くなる。1問ずつなら各回答が次の質問を鋭くする。
- 埋めるべき観点: **解決したい課題／対象ユーザー**、**スコープの境界（やること・やらないこと）**、
  **制約（技術・互換性・パフォーマンス・期限）**、**成功基準（どうなれば完了か）**、**エッジケース**。
- 既にコンテキストから分かることは聞かない。仮説を持って「〜という理解で合っていますか？」と確認する形にする。

不明点が概ね解消し、目的・制約・成功基準を自分の言葉で説明できるようになったら次へ。

### 3. 視覚的な補助資料は「必要なときだけ」

**最初から図を出さない。** 文章で伝わることに図は不要。ただし、フロー・画面レイアウト・
状態遷移・データモデル・アーキテクチャの関係など、**図の方が言葉より確実に速く伝わる論点**が
出てきたときに限り、その場で提案する。

- 提案は**専用のメッセージ**で行い、「図で示した方が分かりやすそうです。作成しますか？」と承認を求める。
- 承認されたら、環境で使える手段で作る（Mermaid 図、`Artifact` による HTML/Markdown プレビュー等）。
  `Artifact` で公開すると承認後にブラウザのタブが開く。使えない環境ではインラインの図で代替する。
- **視覚的な論点が最後まで発生しなければ、図は一切出さない。** 出すこと自体が目的ではない。

### 4. 2〜3案を、トレードオフと推奨付きで提示する

設計の選択肢を1つに決め打ちせず、**2〜3のアプローチ**を並べる。実装空間を可視化し、
ユーザーに本当の選択肢を渡すため。各案について:

- **概要**（何をどうするか）
- **トレードオフ**（メリット／デメリット、複雑さ、影響範囲、既存規約との相性）
- そのうえで **推奨案を1つ明示**し、なぜ推すかを述べる。

ユーザーが案を選ぶ（または混ぜる）まで、設計の詳細には踏み込みすぎない。

### 5. 設計案を段階分けして提示し、各段階で承認を得る

選ばれたアプローチを、**複雑さに応じた段階（フェーズ）**に分けて示す。大きな設計を一度に確定させず、
段階ごとにユーザーの承認を得てから次へ進む。フィードバックの反映が細かく効き、認識のズレを早期に潰せる。

- 小さな変更なら 1 段階で十分。無理に分割しない。
- 各段階では「この段階はこれで確定してよいか？」を明示的に確認する。

### 6. 合意できたら GitHub issue を作る

設計が固まったら、**ユーザーの明示的な承認を得てから** `gh` で issue を作成する。
issue 作成はリポジトリ外に公開される操作なので、勝手に実行しない。

手順は [references/github-issue.md](references/github-issue.md) に従う（issue 本文テンプレート、
`gh issue create` の使い方、ラベル・言語の合わせ方を記載）。作成後は issue の URL をユーザーに伝える。

本スキルの責務はここまで（実装前の合意形成）。実装は issue 化のあと、別途着手する。

## 進め方の原則

- **対話を主役にする。** 上のステップは骨組み。ユーザーの反応に応じて順序や粒度を調整してよい。
- **勝手に決めない／勝手に作らない。** 前提を埋めるのは質問で。issue 作成は承認後。
- **簡潔に。** 各ターンで論点を絞る。長大な説明より、次に決めるべき1点を明確にする。
