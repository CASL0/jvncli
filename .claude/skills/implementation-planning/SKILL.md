# Implementation Planning（issue から実装計画を立ててコメントする）

brainstorming で **要件・設計** まで固めた GitHub issue を入力に、実装に着手する前の
**具体的な段取り（実装計画）**を立て、それを当該 issue の **コメント**として残すためのスキル。

## なぜ issue に実装計画を残すのか

brainstorming の issue は「**何を・なぜ**作るか（要件・採用設計・成功基準）」を記録する。
一方で実装に入る直前には「**どの順で・どこを触り・どう検証するか**」という開発者目線の地図が要る。
それを issue のコメントとして残しておけば、着手前に段取りをレビューでき、実装は地図をなぞるだけになり、
後から「この issue はどう実装する計画だったか」が 1 スレッドで辿れる。

## この計画は issue の情報だけを根拠にする

**コードベースや web は調べない。** Grep/Glob/Read によるコード探索も、WebSearch/WebFetch もしない。
根拠は対象 issue の **本文とコメントだけ**。理由は 2 つ:

- brainstorming の issue は自己完結している（要件・設計・実装ステップ・成功基準が揃っている）。
  同じことを再探索するのは冗長で遅い。
- 正確なファイルパスや関数名といったコードレベルの具体は、コードベースが動くと陳腐化する。
  それらは**実装時に確定する前提**にして、計画は issue が支える粒度で書く方が長持ちする。

issue が黙っている具体は、推測で埋めず「実装時に確定」または「未確定点」として明示する。
これが本スキルの肝であり、**足りない情報を勝手に補完しないこと**が計画の信頼性を保つ。

## いつ使う / いつ使わない

**使う:** brainstorming 等で要件・設計が固まった issue があり、その実装に着手する前に
タスク分解・段取り・テスト方針を立てたいとき。「issue #N の実装計画を立てて」
「この設計 issue をどう実装するか段取りして」など。

**使わない:** 対象の issue がまだ無い（先に brainstorming で issue 化する）。
設計がまだ固まっていない（brainstorming に戻る）。タイポ修正など計画が要らない機械的作業。

## ワークフロー

以下を順に進める。各ステップの狙いを理解した上で運ぶこと。

### 1. 対象 issue を特定する

ユーザーが渡した **issue 番号または URL** を使う。指定が無ければ「どの issue の実装計画か」を尋ねる。
URL からは末尾の番号を取り出す。**自分で探しに行かない**（`gh issue list` 等での探索はしない）。

### 2. issue の内容だけを取得する

計画の唯一の根拠として、本文とコメントを取得する。コマンドは 1 行で実行する。

```
gh issue view <番号> --comments
```

- `gh` が使えて認証済みか不明なら `gh auth status` で確認する。未認証ならユーザーに案内し、勝手に進めない。
- ここで**コードベース・web は一切調べない**（前述「この計画は issue の情報だけを根拠にする」）。
- コメントも読むのは、追加の判断材料や訂正が後から付いていることがあるため。

### 3. 実装計画を組み立てる

issue の **要件・採用する設計案・実装ステップ・成功基準** を、開発者が着手できるタスクへ具体化する。
下記「実装計画コメントのテンプレート」に沿ってまとめる。要点:

- issue の「実装ステップ」より**一段細かく**、それぞれ独立して検証できる単位に割る。依存関係は明示する。
- 影響範囲は issue が触れているレイヤ／モジュール／データフローの粒度で書く。
  issue が名指ししていない具体ファイル・関数は「実装時に確定」と記す。
- 成功基準／受け入れ条件の各項目に、**どう検証するか（テスト観点）**を対応づける。
- issue から読み取れる曖昧さ・置いた前提・要確認事項は「リスク / 未確定点」に残す。埋めない。

### 4. 計画をユーザーに提示して承認を得る

コメント投稿はリポジトリ外に公開される操作なので、**必ずユーザーの承認を得てから投稿する**。
「この内容で issue #N にコメントしてよいか」を、計画本文とともに提示して確認する。承認が取れるまで投稿しない。
指摘があれば反映し、再度確認する。

### 5. `gh issue comment` でコメントを追加する

本文は複数行・日本語を含むため、シェルのエスケープ事故を避けて**一時ファイル**に書き、`--body-file` で渡す。
一時ファイルはスクラッチパッド領域など作業用の場所に置く。コマンドは 1 行で実行する。

```
gh issue comment <番号> --body-file "<本文ファイルのパス>"
```

### 6. 結果を報告する

投稿に成功するとコメントの URL が出力される。その URL をユーザーに伝えて完了。
本スキルの責務はここまで（実装計画の合意とコメント化）。実装コードの着手は別途行う。

## 実装計画コメントのテンプレート

過不足は調整してよいが、**読み取った要点・タスク分解・テスト方針・リスク**は原則残す。
issue 本文の再掲ではなく、**着手可能なタスクへの分解**に価値がある。

```markdown
## 実装計画

<!-- この issue の内容だけを根拠に立てた計画。正確なファイルパス等のコードレベルの具体は実装時に確定する。 -->

### 読み取った要点
<!-- issue から理解したゴール・スコープ・採用設計・成功基準を数行で。認識ズレを着手前に潰すため。 -->

### タスク分解
<!-- 着手順に、独立して検証できる単位で。依存関係があれば明示する。 -->
- [ ] 1. …
- [ ] 2. …

### 影響範囲（issue から読み取れる範囲）
<!-- 触れるレイヤ／モジュール／データフロー。issue が名指ししていない具体ファイルは「実装時に確定」と記す。 -->

### テスト方針
<!-- 成功基準／受け入れ条件の各項目を、どう検証するか。テスト観点を対応づける。 -->

### リスク / 未確定点
<!-- issue から読み取れる曖昧さ・置いた前提・要確認事項。勝手に埋めず、確認すべき点として残す。 -->

### コミット / PR 方針
<!-- bisect しやすい論理単位への分割。issue が変更 type（feat/fix 等）に触れていれば反映する。 -->
```

## 進め方の原則

- **issue の情報だけを根拠にする。** 足りない情報はコード探索や推測で埋めず、未確定点として残す。
- **勝手に投稿しない。** コメント追加は承認後。
- **計画は実装の地図。** issue の再掲ではなく、独立して検証できるタスクへの分解に価値がある。
