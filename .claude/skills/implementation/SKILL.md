# Implementation（実装計画をなぞって実装する）

implementation-planning で issue のコメントとして合意した **実装計画** を入力に、
ブランチを切り、タスクを 1 つずつ実装し、テストと検証を通すまでを担うスキル。

## 3 つのスキルの役割分担

- **brainstorming** — 「**何を・なぜ**作るか」を固め、issue にする。
- **implementation-planning** — 「**どの順で・どこを触り・どう検証するか**」を issue コメントにする。
- **implementation（本スキル）** — その地図を**なぞって実装する**。

この鎖は 1 つ飛ばすと後続が根拠を失う。計画が無いまま書いた実装は、レビュアが
「**何と比べて正しいのか**」を判断できず、スコープも際限なく膨らむ。
だから本スキルの最初の仕事は実装ではなく、**計画が存在することの確認**であり、
それが満たせないときの正しい振る舞いは「実装しない」。

## 計画が無いときの振る舞い（本スキルの核）

**計画が無ければ実装を開始しない。** 状況ごとに差し戻し先が違う:

| 状況 | すること |
|------|---------|
| 対象の issue が無い | **brainstorming** で要件・設計を固めて issue 化する |
| issue はあるが「## 実装計画」コメントが無い | **implementation-planning** で計画コメントを作る |
| 会話の中で段取りを話しただけで、issue コメントになっていない | **implementation-planning** でコメント化する |
| 計画はあるが設計自体が固まっていない／前提が崩れている | **brainstorming** へ戻す |

3 行目は見落としやすい。会話の合意は**コンテキストが切れれば消える**ので、レビューも後追いもできない。
issue コメントとして残っていることが「計画がある」の定義であり、口頭合意はその代わりにならない。

差し戻すときは止まるだけにせず、**最短で計画に到達する道**を提示する。
「実装計画は数分で作れます。issue #N の計画コメントを implementation-planning で作りましょうか？」
のように、次の 1 手を具体的に出す。ゲートは実装を止めるためではなく、**すぐ計画に戻すため**にある。

### 急かされても折れない

「今回だけ」「計画は頭の中にある」「小さい変更だから要らない」「時間がない」——
これらはいずれも計画不在のまま着手してよい理由にならない。手戻りが起きるのはたいてい
「小さいと思った変更」の方で、**急いでいるときこそ地図が無いと迷子になる**。
これはユーザー自身がこのリポジトリの運用として定めたルールなので、その場の要求より優先する。
理由を一度だけ簡潔に伝え、上記の差し戻し先を案内して、計画ができるまで実装には入らない。

### 例外は 1 つだけ、そして広げない

brainstorming が対象外としている機械的作業——タイポ修正、フォーマット適用、原因が自明な 1 行バグ修正、
依存の定期更新——は計画も本スキルも不要で、そのまま直してよい。

ただし **この例外を「今回の変更も実質タイポみたいなもの」と広げないこと。**
広げようとする圧力こそ本スキルが防ぎたいものなので、判断基準は brainstorming と同じにする:
**実装方針に 2 通り以上ありうるか。** ありうるなら機械的作業ではなく、計画が必要。

## ワークフロー

### 1. 対象 issue と実装計画を取得する

ユーザーが渡した **issue 番号または URL** を使う。指定が無ければ「どの issue の実装か」を尋ねる。
**自分で探しに行かない**（`gh issue list` 等での探索はしない）。コマンドは 1 行で実行する。

```
gh issue view <番号> --comments
```

- `gh` が使えて認証済みか不明なら `gh auth status` で確認する。未認証ならユーザーに案内し、勝手に進めない。
- 本文（要件・設計・成功基準）と「## 実装計画」コメントの**両方**を読む。実装中に参照するのは計画だが、
  「なぜそう作るか」は本文にしか書かれていない。
- 計画コメントが複数あれば**最新**を採用する。内容が食い違っていればどちらが有効かユーザーに確認する。
- 計画コメントが見つからなければ、ここで止まって前節の通り差し戻す。

### 2. 計画とコードベースの整合を着手前に確認する

計画は issue だけを根拠に立てられているので、正確なファイルパスや関数名は
「実装時に確定」と書かれている。**それを確定させるのが本スキルの最初の実務**で、
ここで初めてコードを読む。

- `CLAUDE.md` と [.claude/rules/](../../rules/) を確認する
  （[architecture.md](../../rules/architecture.md) のレイヤ責務、[kotlin.md](../../rules/kotlin.md) のスタイル、
  [git.md](../../rules/git.md) のブランチ・コミット規約）。
- 計画の各タスクを、実在するモジュール・ファイル・レイヤへ対応づける。ここで初めて分かる具体は書き留めておく。
- **計画の前提が現在のコードと食い違っていたら、勝手に設計を作り直さずユーザーに提示して確認する。**
  ズレが小さければ確認のうえ進め、設計判断が変わるほど大きければ implementation-planning へ差し戻す。
- 計画の「リスク / 未確定点」のうち **実装の分岐を左右するもの**は着手前に確認する。
  片方を黙って選ぶと、レビューで丸ごとやり直しになりやすい。

### 3. 計画のタスク分解を Todo に写す

計画は issue 側にあるため実装中に見失いやすい。`TodoWrite` に写すと進捗がユーザーにも見え、
「どのタスクが終わったか」が曖昧にならない。

**計画のタスクを勝手に増減させない。** 追加・削除・並べ替えが必要になったら、それは計画の変更なので
ステップ 2 に戻ってユーザーに確認する。

### 4. ブランチを切る

[git.md](../../rules/git.md) に従い、`main` から `<type>/<description>` 形式でブランチを切る
（例: `feat/jvn-search`）。type は計画の「コミット / PR 方針」に合わせる。
既に対応する作業ブランチ上にいるなら、それを使う。

### 5. タスクを 1 つずつ実装する

計画の順序と依存関係を守り、**1 タスクごとに実装と検証を閉じる**。各タスクで:

1. 実装する（[architecture.md](../../rules/architecture.md) のレイヤ責務、
   [kotlin.md](../../rules/kotlin.md) の命名・イディオムに従う。`!!` 禁止、`val` 優先、不変コレクションを露出）
2. テストを追加・更新する（計画の「テスト方針」の項目に対応させる。テストは `shared` に集約する）
3. 該当テストを実行する（`./gradlew :shared:jvmTest`、絞るなら `--tests "*XxxTest*"`）

複数タスクをまとめて書いてから一気に検証すると、失敗の切り分けが難しくなり、
コミットも論理単位に割れなくなる。面倒でも 1 タスクずつ閉じる方が速い。

**このリポジトリ固有の注意:** Edit/Write のたびに `PostToolUse` フックが `./gradlew spotlessApply` を走らせる
（[.claude/settings.json](../../settings.json)）。整形は任せてよいが、フックは**その時点で未使用の import を削除する**。
import だけを先に足す Edit をすると消えてしまうので、**import は使用箇所と同じ Edit で、または使用箇所を書いた後に**追加する。

### 6. 計画のテスト方針と CI と同じ検証を通す

全タスクを終えたら、計画の「テスト方針」の各項目が満たされたことを確認し、CI と同じ検証を通す。
コマンドは 1 行ずつ実行する。

| 目的 | コマンド |
|------|---------|
| フォーマット検証（CI と同じ） | `./gradlew spotlessCheck` |
| テスト | `./gradlew :shared:jvmTest` |
| カバレッジ（行 80% 下限） | `./gradlew :shared:koverVerify` |
| ビルド全体（必要なら） | `./gradlew build` |

**失敗を残したまま次へ進まない。通らないものを通ったことにして報告しない。**
直せない失敗があれば、出力とともにその事実を伝えて判断を仰ぐ。

### 7. コミットは計画の方針に沿って、指示を得てから

計画の「コミット / PR 方針」に従い、[git.md](../../rules/git.md) の Conventional Commits で
**bisect しやすい論理単位**に分ける（各コミット時点でビルド・テストが通る状態を保つ）。

計画にコミット方針が書かれていても、**コミットの実行はユーザーが求めたときに行う**。
push と PR 作成はリポジトリ外に影響するので、**明示的な承認を得てから**実行する。

### 8. 完了を報告する

計画と実装の対応が追えるように、次を伝えて完了とする。

- 計画のタスクごとの結果（完了 / 未対応、未対応なら理由）
- 実行した検証コマンドとその結果（失敗があればそのまま伝える）
- **計画からの逸脱**とその理由（ステップ 2 で確認済みのものも含めて明記する）
- 残った未確定点・フォローが必要な点

## 進め方の原則

- **計画が無ければ実装しない。** 止まるだけでなく、計画に戻る最短の道を示す。
- **計画は地図、コードベースが現実。** 食い違いは勝手に埋めず、ユーザーに確認する。
- **1 タスクずつ、都度検証。** まとめて書いて最後に検証しない。
- **勝手に外へ出さない。** commit は指示を得てから、push / PR は承認後。
- **報告は正直に。** 失敗・未対応・逸脱を隠さない。
